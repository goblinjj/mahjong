# 多帧检测融合：消除实时识别的张数与类别抖动

日期：2026-07-26

## 问题

摄像头实时识别一副 13 张的牌时，结果在 12 张和 13 张之间反复跳动；部分牌的类别也会在相邻两张之间跳变（如 5万 ↔ 6万）。没有观察到多检或重复框。

根因有三处：

1. **没有任何时序融合**。`app.js:206` 每帧直接用最新一帧的检测结果覆盖 `liveDetections`，确认按钮取的就是最后那一帧。单帧 YOLO 在置信度阈值附近本来就会闪。
2. **条带 letterbox 浪费分辨率**。`recognition.js:246` 把 40:9 的条带塞进 640×640，`scale` 由宽度决定，上下补了 70% 以上的灰边，牌在模型输入里只剩几十像素高，正好卡在 YOLOv8n 的能力边缘。
3. **未利用「牌排成一行」的几何先验**。牌等宽、等高、基线共线、间距均匀，漏检会在几何上留下明显空洞。

本设计解决第 1 点，并顺带利用第 3 点的一部分。第 2 点见「不在本次范围」。

## 方案选择

考虑过三条路线：

- **A. 几何锚定的多帧轨迹投票**——把「牌」从「一帧里的一个框」升级为「一条跨帧轨迹」，用出现率和类别投票聚合证据。推理开销零增加。
- **B. 几何补齐**——拟合一行牌的格位网格，对空洞位置单独裁剪重推理。单帧质量提升明显，但要额外推理，且副露/间隔摆放等边界情况复杂。
- **C. 分块推理**——把宽条带切成两个重叠块逐帧轮流推理，有效分辨率翻倍而帧率不变。

**采用 A**，并入 B 中最便宜的一部分（离群框剔除）。C 留作后续阶段。

理由：A 的收益最确定、开销为零，且它建立的「多帧证据聚合」框架是 C 的前提——先有框架，C 才只是往里多塞一个证据源。反过来先做 C，单帧再好也仍会闪。

### 为什么不用陀螺仪

陀螺仪只知道手机怎么动，不知道牌在哪。它在本方案中唯一的位置是「运动闸门」（手机在动时该帧类别判断不可信，不计入投票），而同样的效果用图像帧差即可实现，不需要 iOS 13+ 那套必须由用户手势触发的 `DeviceMotion.requestPermission`。

更关键的是：手抖导致的整行平移，本方案用**位移中位数补偿**直接从图像测得（见下），测的是「牌在画面里实际移动了多少像素」；陀螺仪只能测「手机转了多少角度」，还需要知道拍摄距离才能换算成像素位移，绕一大圈精度反而更差。

结论：本次不引入陀螺仪。A 上线后若仍有残余抖动，再考虑加图像帧差的运动闸门。

## 性能前提

实测约 2~3 fps（WASM 单线程 YOLOv8n 640×640）。「端稳 1~2 秒」≈ 3~5 帧，融合窗口据此定为 5 帧，稳定判据最快 5 帧达成。所有参数按这个帧率标定。

## 架构

### 新模块 `js/detection-fuser.js`

纯逻辑、不依赖 DOM，与 `mahjong-engine.js` / `analyzer.js` 同级。**这样它能被 `js/test-engine.js` 直接 import 做单元测试**——融合逻辑无法靠对着摄像头肉眼调准，必须能喂合成序列跑断言。

对外接口三个方法：

```js
const fuser = new DetectionFuser(config);
fuser.push(detections, now)  // 喂一帧原始检测 → 返回融合快照
fuser.reset()                // 换牌/切模式/大幅移动时清空
fuser.snapshot()             // 纯读取最近一次 push 的结果，无副作用
```

`push` 返回：

```js
{
  state: 'collecting' | 'unstable' | 'stable' | 'degraded',
  tiles: [{ tileIndex, confidence, bbox }],  // 与现有 detections 结构一致
  pending: 2,        // 「拿不准」的轨迹数，用于提示用户
  frames: 4,         // 已累积帧数
  progress: 0.8      // 0~1，供 UI 画稳定度
}
```

`progress` 定义为「距离 STABLE 还差多远」，取两个分量的较小值：
`min(frames / windowSize, consecutiveConsistentFrames / stableFrames)`。
存在待定轨迹、或一张牌都没检出时，强制封顶在 `pendingProgressCap = 0.99`——这两种情况下无论攒多少帧都不会稳定，进度条不该显示成满格。（对着空白处时每帧签名都是空串，连续一致计数会无限增长，若不封顶会出现「什么都没识别到但进度满格」。）

`tiles` 结构与现有 `liveDetections` 完全一致，因此 `drawOverlay`、`showDetectionPreview`、确认流程无需改动，只是数据源从「最后一帧」换成「融合结果」。这顺带消除了叠加框自身的抖动。

`now` 由调用方传入而非 fuser 内部取时钟，使超时逻辑也可在测试中喂假时间验证。

### 数据结构

每条轨迹：

```js
{
  id,                  // 自增
  cx, cy, w, h,        // EMA 平滑后的位置尺寸
  // 滑动窗口内的命中记录。出现率取它的长度，类别票在它上面聚合 ——
  // 两者本就一一对应，合并为一个数组，旧证据随窗口一起过期。
  hits: [{ frame, tileIndex, conf }...],
  bornFrame,           // 出生帧序号，用于新生轨迹的出现率分母
  lastFrame,
}
```

## 关联规则：位移中位数补偿 + 两遍贪心匹配

手持时整行牌随手抖整体平移。处理流程：

1. 用宽松阈值（`matchRadiusCoarse = 1.0` 牌宽）粗匹配上一帧轨迹与本帧检测
2. 取所有匹配对位移的**中位数** dx/dy（中位数抗离群，个别错配不影响补偿量）
3. 将全部轨迹平移 dx/dy
4. 用严格阈值（`matchRadiusFine = 0.4` 牌宽）重新匹配

匹配代价 = 中心点距离 / 平均牌宽。牌紧贴排列，相邻牌中心距约等于 1 个牌宽，0.4 牌宽的阈值足以区分相邻牌而不串位。目标最多 14 个，按置信度降序贪心匹配即可，无需匈牙利算法。

未匹配的检测 → 新建轨迹。未被匹配的轨迹 → 该帧记 miss。

轨迹位置用 EMA 平滑后输出，避免预览框抖动。

**离群框剔除**（并入自 方案 B）：在进入匹配前，取本帧所有框高度的中位数 `hMed` 与底边 y 的中位数 `yMed`，丢弃满足以下任一条件的框：

- `h < 0.6 × hMed` 或 `h > 1.6 × hMed`（尺寸明显不合群）
- `|底边 y - yMed| > 0.5 × hMed`（不在同一条基线上）

本帧框数少于 4 个时跳过剔除——中位数在样本太少时不可靠，宁可不剔。

## 轨迹三态

每条轨迹按其在滑动窗口（`windowSize = 5` 帧，约 2 秒）内的出现率分档：

| 出现率 | 状态 | 处理 |
| --- | --- | --- |
| ≥ 0.7 | 确认存在 | 计入输出 |
| 0.3 ~ 0.7 | **待定** | 不计入输出，但**阻止进入 stable** |
| < 0.3 | 噪声 | 老化删除，不阻止稳定 |

新生轨迹的出现率分母取 `min(帧数 - bornFrame, windowSize)`。

`presentRate` 同样必须避开可达边界（原因见下节，这一点是在实现阶段第三次踩到同一类问题才补上的）。可达出现率集合为 {0.2, 0.25, 0.333, 0.4, 0.5, 0.6, 0.667, 0.75, 0.8, 1.0}：

- 取 0.6：`3/5 === 0.6` 在 IEEE754 下精确相等，于是「每隔一帧出现一次」的幻影框会随帧奇偶在 0.4 与 0.6 之间跳，在 0.6 的那些帧上被判为确认存在并带着 `pending === 0` 进入输出——降级路径下直接进用户手牌。
- 取 0.7：落在 0.667 与 0.75 之间，两侧都有余量。

类别投票在轨迹内按置信度加权聚合（只统计窗口内的帧，见下节），胜出类别占比需 ≥ `voteRatio = 0.7` 才算收敛，否则该轨迹同样计入「待定」。

**阈值必须避开可达边界**。票在 `windowSize = 5` 的窗口内聚合，因此一条每帧都被命中的轨迹，两个类别只可能分成 5:0 / 4:1 / 3:2，比例只能取 **1.0 / 0.8 / 0.6**：

- 取 0.5：两类时胜出方占比恒 ≥ 0.5，闸门失效。
- 取 0.6：恰好等于可达最小值，`ratio >= 0.6` 仍恒成立，闸门同样失效——这一点是在实现阶段才发现的。
- 取 0.7：落在 0.6 与 0.8 之间，两侧都有余量，且不存在浮点边界问题。语义是「5 帧里至少 4 帧一致才算收敛」。

`presentRate`、`pendingRate`、`voteRatio` 三者都与 `windowSize` 耦合，**改动其中任何一个都必须重算可达值集合并确认阈值落在两个可达值之间**，否则闸门会再次悄悄失效。这一类错误在本项目已经发生过三次（位移 reset、`voteRatio`、`presentRate`），每次的表现都是「阈值恰好落在指标可达范围的边界上，判据恒真或恒假」，且都不会报错，只会静默失效。

### 为什么要有「待定」这一档

降低置信度阈值后必然出现若隐若现的框。若只做二分，它们要么污染结果、要么被静默丢弃——**静默丢弃正是当前「一会儿 12 张」的问题，只是变成了稳定地给出 12 张，更糟：用户会拿到一个看起来很确定的错答案**。

让待定轨迹阻止稳定并提示「有 N 处不确定」，用户就知道该调整角度或光线。

## 配套阈值调整

`recognition.js` 的 `confThreshold` 从 **0.5 降到 0.3**。降阈值会引入更多假阳，但假阳的特征是位置随机、不连续，出现率过滤天然能压掉——**先降阈值把弱证据放进来，再用时序把噪声滤出去**，这是整套方案的核心交易。

NMS 阈值 `iouThreshold = 0.35` 不变。

## 状态机

```
COLLECTING ──帧数≥3──> UNSTABLE ──判据全满足──> STABLE
                          │  ▲                    │
                    超时8s │  └────判据被打破──────┘
                          ▼  ▲
                      DEGRADED
                          │  │
                          └──┘ 判据满足则升到 STABLE
```

DEGRADED 不是终态：降级后若判据重新满足（用户挪了个角度、光线变好），直接升到 STABLE，按钮恢复正常绿色。降级只是解除「按钮永远不亮」的锁死，不是放弃。

`reset()` 会同时清空超时计时器，下一次进入 UNSTABLE 重新开始计时。

进入 **STABLE** 需同时满足四条：

1. 本帧无类别冲突（无任何轨迹收到与其既有胜出类别不符的检测，见「场景切换」一节）
2. `pending === 0`（无出现率处于 0.3~0.7 之间、或类别未收敛的轨迹）
3. 输出非空（`tiles.length > 0`）
4. 连续 `stableFrames = 3` 帧输出的牌多重集（`tileIndex` 排序后）完全一致

第 4 条是最后一道闸：前三条判断单帧快照，第 4 条要求该快照本身稳住。合起来最快 5 帧达成，在 2~3 fps 下约 2 秒。

### 场景切换：靠票过期，不靠位移检测

**新旧牌的投票混在一起，用户会拿到一副从未存在过的手牌**——这是本机制最危险的失效模式。

本文档最初的方案是「全局位移中位数超过 1.5 个牌宽就 reset」。**该方案已在实现阶段被证伪并废弃**：牌是周期排列的（周期 ≈ 一个牌宽），而 `matchRadiusCoarse` 正好是 1.0 个牌宽，最近邻搜索永远折叠到最近的那个周期上。实测真实位移 40px 估成 −2、80px 估成 −4、400px 估成 −20——估计值恒落在 ±半周期内，1.5 牌宽的阈值**永远不可能被触及**，那条 reset 是死代码。

现行方案不去检测「场景变了」，而是让旧证据自然失效：

- **类别票与 `hits` 共用同一个滑动窗口**（两者本就一一对应，合并为一个数组）。场景一变，旧票在 `windowSize` 帧内全部过期，无需任何阈值。
- **本帧存在类别冲突时不得进入 STABLE**。窗口化留下一个 1~2 帧的缺口：刚换牌时旧票仍暂时占多数，若不拦，fuser 会绿灯报出旧手牌。判据是「本帧有任何轨迹收到与其既有胜出类别不符的检测」——一个布尔标志的成本。

位移估计本身保留：小位移它是准确的（8px 估成 8、20px 估成 20），手抖补偿依然有效，被废弃的只是建立在它之上的 reset 触发器。

显式 reset 仍然存在：切换模式、取消预览、确认之后。

### 兜底：DEGRADED

从进入 UNSTABLE 起计时，超过 `degradeAfterMs = 8000` 仍未 STABLE 则降级：确认按钮解禁，使用次要样式与明确文案「⚠️ 仍不稳定，仍要确认 (N 张)」。

输出只含「确认存在」的轨迹，**待定的不纳入**——它们类别未收敛，纳入等于随机给一张错牌，比少一张更坏。

没有这条兜底，光线差的场景下按钮会永远不亮，功能直接不可用。有了它，用户拿到 12 张、应用后落到手动选牌面板（`btnDetectApply` 末尾已 `switchMode('manual')`），缺的那张自行补上即可。

## UI 改动

### 1. `#live-count-badge` 文案随状态变

| 状态 | 文案 |
| --- | --- |
| COLLECTING | `采集中 2/5` |
| UNSTABLE，有待定 | `有 N 处不确定，微调角度或光线` |
| UNSTABLE，无待定 | `稳定中…` |
| STABLE | `✓ 已稳定 · 13 张` |
| DEGRADED | `⚠️ 识别不稳定` |

该 badge 带 `aria-live="polite"`，以 2~3 fps 改写 `textContent` 会让读屏软件念个不停。**只在 state 或张数变化时才写 DOM**，值未变则跳过。

### 2. 取相框虚线颜色随状态变

复用已有的 `#camera-container::after`，加一个 CSS 变量：采集中灰、待定黄、稳定绿、降级橙。用户用余光即可判断该不该按，无需读文字。

### 3. 确认按钮

非 STABLE / DEGRADED 时保持 disabled；STABLE 时 primary 绿色；DEGRADED 时次要样式加警告文案。

### 4. `app.js` 接线

`detectionTick` 中现有的：

```js
liveDetections = result.tiles;   // app.js:206
liveImageData = imageData;
updateLiveBadge();
```

改为把 `result.tiles` 喂给 fuser，用返回的 `snapshot.tiles` 赋给 `liveDetections`，再按 `snapshot.state` 更新 badge 与按钮。

`drawOverlay()`、确认按钮回调、`showDetectionPreview` 均不改动——它们看到的数据结构未变。`liveImageData` 仍存最近一帧原图（融合 bbox 已补偿到最新帧坐标系，可对齐）。

`stopDetectionLoop()` 与切换模式处需调用 `fuser.reset()`。

## 参数

集中在 `DEFAULT_CONFIG`，构造时可覆盖，真机调参只改一处：

```js
{
  windowSize: 5,          // 滑动窗口帧数
  presentRate: 0.7,       // 确认存在的出现率（与 windowSize 耦合，见上）
  pendingRate: 0.3,       // 低于此值视为噪声（与 windowSize 耦合，见上）
  pendingProgressCap: 0.99, // 有待定或零张时 progress 的封顶值
  voteRatio: 0.7,         // 类别投票胜出占比（与 windowSize 耦合，见上）
  stableFrames: 3,        // 输出连续一致所需帧数
  matchRadiusCoarse: 1.0, // 粗匹配阈值（牌宽倍数）
  matchRadiusFine: 0.4,   // 补偿后精匹配阈值（牌宽倍数）
  degradeAfterMs: 8000,   // 降级超时
}
```

外加 `recognition.js` 的 `confThreshold: 0.5 → 0.3`。

## 测试

在 `js/test-engine.js` 新增一个 fuser 测试块，配一个构造合成检测序列的辅助函数（给定牌列表生成一行等间距 bbox）。六个场景，全部在 node 中运行，不需要摄像头：

1. **漏检修复**：13 张，第 3 帧抽掉第 7 张 → 5 帧后输出仍为 13 张
2. **类别投票**：某位置 4 帧判 5万、1 帧判 6万（占比 0.8 ≥ 0.7）→ 输出 5万；两类交替（占比 0.6）→ 不收敛，计入待定
3. **平移补偿**：每帧整行 +8px → 不产生新轨迹，仍 13 张
4. **假阳抑制**：随机位置只出现 1 帧的框（出现率 0.2 < 0.3）→ 不进输出，且不阻止 STABLE
5. **待定阻止稳定**：某轨迹 5 帧中出现 2 帧（出现率 0.4）→ `state !== 'stable'` 且 `pending === 1`
6. **场景切换**：换一副牌（位置不变、类别全变）→ 过渡帧不得报 STABLE，旧票过期后收敛到新牌并回到 STABLE

这六条覆盖机制的每一个分支。

真机验证用 `npm run preview:pages`（`npm run dev` 下 Service Worker 被跳过，且此改动不涉及 SW，但保持一致的验证方式）。

## 不在本次范围

- **分块推理（方案 C）**：把条带切成两个重叠块逐帧轮流推理，有效分辨率翻倍。收益需实测，且要求轨迹关联处理「本帧只覆盖半边」的情况，稳定判据随之复杂。留作后续阶段。
- **模型域偏差**：当前模型基于 Roboflow 公开数据集（42 类映射）训练。多帧投票能救「偶尔判错」，救不了「在特定牌面和光照下系统性判错」——若某张牌 80% 的帧都判成另一张，融合只会稳定地给出错误答案。这属于补数据重训的范畴，是另一个项目。实施本方案后若发现是固定几种牌一直错，即为此类问题。
